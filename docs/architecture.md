# Platform architecture design

FRA-003, design version 2, 2026-10-04. Corrected documentation design founder-accepted on 2026-10-04; all runtime behaviour described here is planned. This design approves no provider, SDK, pricing, installation, external execution or product implementation. It derives from the [specification](product-specification.md), [task plan](implementation.md) and accepted [founder inputs and deferrals](founder-brief.md). No external market or technical compatibility claims are made.

## Contract conventions

Propose one local Python process with explicit validators, a deterministic coordinator, SQLite and provider adapters. Exact Python/tool choices await FRA-004 prerequisites. The contracts below are logical schemas, not application code or installed database definitions.

Every record has required `schema_version: positive integer` (initially 1), `id: UUID string`, `created_at: UTC RFC3339 timestamp`, `created_by: actor ID`, `mode: demo|live`, and `provenance: object {origin: human|model|tool|derived|synthetic, producer_role: string, input_versions: version-reference array, method: string, limitations: string array}`. Arrays may be empty only where explicitly allowed or no references exist. Unknown enum values, missing required fields and unknown schema versions fail validation. Unknown numeric values use null with a reason, never zero. Text must be nonempty unless stated otherwise; numbers must be finite. Dates use ISO dates; partial/unknown source dates retain original text and precision rather than inventing a day.

`T?` means nullable, explicitly stored as null when unknown/not applicable with an accompanying reason; other fields are required. A version reference identifies immutable `(artifact_id, version)`; an ID reference identifies a record of the named type. Every business record belongs to an artifact version using required `artifact_version: version reference`; artifacts themselves use the version contract below. References must exist, have compatible scope/mode and pass type validation, except the narrowly scoped offline-demo authority relationship below. Captured external IDs never replace internal IDs. Live means actual provenance, not verified truth, current evidence or permission. Mixed synthetic inputs taint derived outputs as demo; they cannot be relabelled live. A live workflow may display demo material separately but cannot count it toward a live gate.

Actors have `kind: human|agent|system`, `display_label: string` (no private identity required) and `external_identity_ref: string?`. Review assignments have `human_actor_id`, `role`, `scope_ref`, `designated_by: founder actor ID`, `effective_at`, `revoked_at?`, `qualification_ref?`, `independence_required: boolean`. Only a human can hold an acceptance assignment. The same founder actor may hold several roles. Store `self_review: boolean` on acceptance, compare underlying actor IDs and disclose shared roles. A different role label or a second model does not establish independent human review.

Bootstrap actor, branch and artifact identities are allocated together before their content references are validated in the creation transaction; no record requires a self-referential artifact envelope. Actors and assignments use their own identity tables and common provenance fields. Task/attempt status is a mutable projection backed by append-only versioned run/output/usage records. For actors, demo means a synthetic identity, never the actual founder's authority.

### Immutable records, criteria and authority relationships

Canonical evidence never stores later approval/review IDs or mutable verification results. Decisions, claim verification reviews and gap reviews are separate immutable records targeting exact artifact versions. Reverse acceptance/review links, claim verification state and reservation state are derived projections, not edits to canonical payloads. Claim verification reviews use the fields specified in Evidence link above; current results are derived from applicable reviews and invalidation events. Stage criteria and integration verification obtain acceptance through decision-target relationships.

A criterion reference is `{criteria_version: (artifact_id, version), item_key: string}`. The key must exist uniquely in that exact Stage criteria version. Gaps use these references; gate result keys are scoped to their evaluation's pinned `criteria_version`. No bare criterion ID or key may resolve to a latest version. Changed criteria require new evaluation and review of affected gaps.

Derivation edges describe inputs used to produce artifact content and form an acyclic graph. Review-target, decision-target and assignment/authority relationships are separately typed references, not derivation edges back from evidence to a later review. Gate reliance combines these relationships with current validity; changes or revocation invalidate dependent gate evaluations without rewriting evidence or introducing derivation cycles.

### Offline demo execution authority

The run's `authorisation_decision_id` must reference a real human authorisation record (live mode, human provenance and actual founder actor), explicitly scoped to offline demo execution, its exact run specification/configuration versions, local tools/data, limits and expiry. This is the sole cross-mode authority-reference exception: the demo run may reference that live authorisation and its real actor/assignment for execution checks only. The authorisation may target demo configuration versions; these target relationships do not derive evidence or taint the authority record as synthetic. Synthetic inputs to evidence derivation still taint outputs as demo.

The broker checks this real authority before starting or resuming the demo. Synthetic lifecycle decisions and simulated assignments exercise demo gates only; they cannot authorise execution, network access or live gates. Real permission to run a demo establishes no lifecycle acceptance, customer evidence, provider readiness or live spending authority. This design document itself authorises no demo execution.

## Role handoffs

All handoffs pin input/output versions and require contract validation, current dependencies, authorised scope and named human acceptance assignments. Reviewers may read unaccepted material for review only. Operational downstream use waits for acceptance. A rejected/missing/invalid output records a failure or gap, blocks dependent tasks, and routes rework to its producer; no fabricated placeholder or silent demo fallback. This common failure rule applies to every row.

## Execution and stage decisions

Execution status is a task/run projection, separate from artifact freshness, gate eligibility and human decisions. `pending -> running` requires valid accepted dependencies, permission and reservations where applicable. `pending -> blocked` records missing prerequisites. `running -> succeeded` requires validated durable output; `running -> failed` records a known failure; `running -> blocked` records uncertain outcome or exhausted limits with a checkpoint. `failed|blocked -> pending` requires documented resolution, compatible inputs and retry eligibility. A succeeded task is retained historically; changed inputs create a new task generation rather than rewriting its success. Runs succeed when scheduled work completes, even if the resulting recommendation is stop; they never implicitly pass a stage.

| Stage choice | Preconditions and effect |
| --- | --- |
| Proceed | Designated human decides against a fresh eligible evaluation; mandatory criteria defined/met, mandatory evidence present, accepted dependencies current, required gap reviews/resolutions and approvals present. Recheck atomically when advancing. New execution still needs task/tool authority. |
| Rework | Record producer/task, failed criteria, required corrections and destination; invalidate affected downstream work and request new versions. Does not advance stage. |
| Pivot | Human records rationale, parent branch/version and new brief/opportunity branch. New branch begins with its own criteria, dependencies and approvals; explicitly reused evidence must be reassessed. Previous branch and decisions remain intact and are marked superseded for this lineage, not deleted or retroactively passed. |
| Defer | Record blockers, owner and resumption conditions; checkpoint and suspend scheduling. Limits/permissions/criteria must be rechecked on resume. |
| Stop | Close branch to new scheduling, preserve artifacts/ledger/history; reopening requires explicit new human authorisation and versioned branch decision. |

Blocker codes include `undefined_criteria`, `missing_evidence`, `unreviewed_gap`, `critical_gap`, `missing_owner`, `missing_approval`, `failed_dependency`, `stale_input`, `mode_mismatch`, `permission_denied`, `integration_mismatch`, `usage_exhausted`, `unknown_outcome`. Missing mandatory evidence, undefined criteria, unreviewed potentially critical gaps, absent approvals and failed dependencies always block proceed. An AI may recommend any choice but cannot record a human decision. Without human input the coordinator records blocked status and a recommendation; it does not invent a defer approval. A human may choose rework/defer/stop or a new pivot branch while the old gate remains blocked.

## Versioning and recovery

Fingerprint a canonical UTF-8 JSON manifest with sorted object keys, preserved array order, UTC timestamps, explicit nulls and decimal strings, using SHA-256. It contains exact input artifact versions/hashes, graph and contract versions, criteria, prompt/template and calculation versions, configuration fingerprints, tool/permission and usage policies, mode and branch. Do not include secret values. Hash sanitised payloads and opaque credential revisions. Store the manifest as well as the digest so mismatches can be explained.

Record derivation dependencies on input content, criteria and configuration, and separate gate-reliance relationships for approvals, reviews, authority and source freshness. Changes create new versions and append invalidation events for the transitive downstream closure. Unrelated branches remain valid. Old approvals stay in history but cannot authorise changed artifacts; fresh evaluations and acceptance are required. Source expiry can invalidate reliance without changed content. Prompt/provider changes invalidate affected derived outputs, not the historical fact that a source was captured. Cycles in scheduling or derivation dependencies are rejected.

Resume validates checkpoint hashes, schemas, database revision lineage, inputs, graph, unresolved dispatch ledger, current permission/approval expiry, integration readiness and limits. Reuse only durable, compatible succeeded outputs. If a checkpoint is stale, preserve it, record why, and reconstruct a new generation from durable current dependencies. Never infer an interrupted call failed merely because output is absent. Local publication is idempotent via unique task-generation/attempt/output keys and atomic transactions; this is not an exactly-once guarantee for external calls.

Retry policy requires finite `max_attempts`, per-attempt timeout, total deadline and capped backoff; values must be configured and approved before dispatch. Every attempt counts, including hidden transport retries (disable or explicitly account for them). Contract, permission, unsupported configuration, evidence and hard-budget errors do not automatically retry. Known transient failures retry only within policy and fresh reservations. Interrupted/timeout calls with uncertain provider outcome enter `unknown_outcome`, retain possible charges/token reservations and block automatic replay. An authorised status lookup or provider receipt may reconcile them; lookup itself needs permission and limits. Provider idempotency keys can reduce duplication only where verified, never promised generally. If certainty remains unavailable, a human must explicitly accept duplicate-charge risk and authorise a new attempt with enough additional reserve, or defer/stop. Human approval cannot bypass an unverifiable hard cap. No reservation is released solely due to timeout or age. Resumption also requires any backup recovery boundary below to be resolved.

## Minimal SQLite proposal

Use one local database outside Git. Canonical record content lives in immutable artifact payloads; relational tables index identities, relationships and safety-critical counters. This avoids a separate table for every report while preserving foreign keys. JSON validation is performed by the application; SQL constraints are a second boundary, not the full contract validator. Exact SQLite/runtime features require later compatibility verification.

Enable foreign keys on every connection; use NOT NULL for required columns and CHECK for enums/booleans/nonnegative counts. Deletion of referenced history is RESTRICT. Validate cross-record mode, actor authority, branch compatibility, acyclicity and JSON contracts in the same transaction as insertion. Later reviews/approvals insert separate records and target relationships; no forward approval field is added to immutable evidence. Absence of applicable acceptance blocks use. Immutable payloads remain unchanged: decision indexes and validity projections derive subsequent approval state. Real actor/customer identity mapping and raw customer records stay in a separate protected store; only sanitised opaque references enter this database or exports.

Transaction boundaries:

1. Validate and insert artifact versions, dependency edges, evidence indexes and local task completion atomically; bump database revision. A failed write publishes no success.
2. Under a single writer transaction, check current authority/configuration/limits and allocate reservation plus prepared attempt; commit before any external call. Mark dispatch intent durably before network dispatch. A crash between intent and send is conservatively uncertain. Never hold a database transaction open across network calls.
3. Append usage observation and durable output, settle only known usage, update task status and checkpoint atomically. A crash after provider response but before this commit leaves an uncertain attempt requiring reconciliation.
4. Re-evaluate fingerprint and authority inside the human-decision/advancement transaction; insert decision and state event atomically. Invalidation events and current projections update together. Concurrent stale decisions fail optimistic revision checks.

Store canonical sanitised artifact bytes in SQLite for the initial design. JSON/Markdown files are regenerable exports, written to a temporary file then atomically renamed after commit; failed export does not lose the canonical artifact. Private data never enters exports. This avoids pretending filesystem writes and database commits form one transaction.

Database migration versions and record schema versions are separate. Apply ordered checksummed migrations in a transaction with a backup outside Git, after explicit migration authorisation; reject newer unknown schemas and changed migration checksums. Failed migrations roll back without partial upgrade. Preserve original artifact payloads/hashes and use explicit derived schema versions for transformations; do not rewrite historical decisions. Recovery uses the boundary protocol below before any dispatch, including attempts absent from the restored database. No migrations or database are created by FRA-003.

### Backup recovery boundary

An older backup may omit entire attempts, reservations and receipts. Database revision/checkpoint consistency alone cannot detect this loss. Before each live dispatch, durably append an intent containing database lineage, monotonic dispatch sequence, attempt/reservation IDs, account/configuration, timestamp and per-dimension bounds to a small local append-only dispatch journal outside the database backup/restore set; failure to append blocks dispatch. Then send. A journal intent without a receipt remains uncertain. This is one process and a local file, not a distributed service or exactly-once guarantee.

Every restore starts in dispatch-blocked recovery mode. Record an immutable recovery boundary with backup identity/hash, lineage and backed-up dispatch high-water mark, restore time, independently retained journal high-water mark and coverage, account scopes, missing sequence/time interval, evidence references and resolution status. Compare the restored ledger against the independent journal; recreate absent attempts/reservations by their original IDs and retain uncertain exposure. A journal restored from the same backup cannot establish coverage. If the independent journal is missing, truncated or cannot establish complete coverage, treat the interval from the last independently proven boundary through dispatch freeze as unknown, including possibly missing calls; never infer zero activity from an empty ledger.

Reconcile against independently retained receipts or authorised provider history where available; recovery lookups require separate bounded authority outside the blocked normal dispatcher and their own durable accounting. If provider history is unavailable, preserve unknown values and conservatively charge the full evidenced upper bound for each missing attempt/dimension, or for the entire interval where individual attempts are unknown. Record a human-reviewed recovery accounting decision, its evidence, scope, bounds and unresolved uncertainty. Unknown history cannot be marked measured or released. If no defensible finite bound exists for a required hard cap, dispatch remains blocked: defer/stop until sufficient evidence or independently enforceable coverage exists. New run IDs, restored budgets or human risk acceptance cannot erase historical exposure.

Unblock only after the boundary has complete coverage, every missing interval is reconciled or conservatively accounted for without overlapping charges, and current authority and all applicable limits pass. Keep boundary/accounting records in SQLite and preserve the recovery boundary alongside the independent journal so another restore cannot silently erase it. Correlated loss of both stores is handled as unknown coverage, not proof of safety.

## Provider and usage boundaries

The provider-neutral interface accepts `request_id`, capability, sanitised typed payload, configuration version, deadline, output bound, permission reference and reservation reference. It returns normalised content/source captures, provider request reference, actual model/service revision when available, usage observations and redacted errors with known/unknown dispatch outcome. Search returns source captures; it does not verify claims. Generation returns proposals; it cannot issue human approvals. Adapter capability metadata must declare supported bounds, error mapping, retry behaviour and whether cost/token measurement is available. No provider, SDK or pricing is approved here.

Readiness is keyed to the exact configuration fingerprint and capability. A changed adapter, provider/model/service, endpoint/region, account or credential revision, capability set, relevant parameters, privacy policy, retry/transport/bounds policy, or expired verification invalidates readiness; changes require FRA-023 re-verification and human technical acceptance. Live research requires FRA-011 plus all matching FRA-023 records and separate research authorisation/limits. FRA-023 preflight uses its own explicit verification authority, not a circular requirement for already passed integration. It cannot authorise opportunity research. Demo cannot use live transports even if configured credentials exist.

Enforce call-count caps locally by reserving all attempts before dispatch. Enforce token caps only when a verified conservative input bound and provider-enforced output bound cover all billable categories, including internal reasoning/cached/tool tokens as applicable; otherwise label the limit unverifiable and block if it is a hard requirement. Non-token services use an explicit not-applicable token policy plus bounded call units. Outstanding and uncertain reservations count against remaining capacity. For each cap, use the per-dimension accounting below; settled observations replace covered reservation amounts rather than adding to them. Retries require new reservations. Over-bound reported usage records a policy breach, blocks further calls and triggers review; do not clamp reported usage to the cap.

Money estimates are forecasts, not enforceable hard spend guarantees. A hard monetary cap permits dispatch only with verified conservative bounds covering billable units, retry risks, applicable fees/currency treatment, or a verified provider-side hard cap sufficient for the activity. Unknown pricing, unknown chargeable units or an estimate alone cannot assure a hard cap and block the call. Unknown costs stay null, never zero; even nominally free access needs verified terms and applicable limits. A separately approved estimate-based policy may allow uncertain final cost only within explicit spending authority, visible estimates and call/token controls; it must not be presented as a hard money cap. The founder has approved neither such a policy nor numeric live limits. Exhaustion blocks new dispatch, saves checkpoint and recommends defer; human resumption requires approved policy changes and fresh checks.

### Partial usage reconciliation

Account separately for calls, input/output tokens (and any other billable token category), and money by currency. Each dimension has known consumption `K`, outstanding reserved amount `R`, unknown-exposure flag/reason `U`, and finality. Unknown exposure is covered by `R` only when a verified conservative bound exists; otherwise it is unbounded and blocks any required hard cap. Capacity is cap minus the sum of `K + R` over distinct attempts and nonoverlapping recovery intervals. `U` describes uncertainty, not an extra numeric charge. Estimates never become known consumption.

Before dispatch, `K=0` and `R` holds the full verified bound. After uncertain dispatch the possible call is retained in `R` until established; a known attempted call moves one call unit from `R` to `K` even if tokens and money remain unknown. Partial cumulative consumption moves only that dimension's confirmed amount into `K`, with `R = max(bound - K, 0)` while further usage remains possible. Thus known tokens do not release money, and a cost receipt does not settle calls or tokens. Only authoritative final totals for that dimension release its residual reserve; proven not-sent releases all dimensions with evidence. Timeouts, elapsed time and successful output alone never prove final usage. Over-bound observations retain actual consumption, block dispatch and trigger policy review; further unbounded exposure remains explicit.

Each reconciliation is an append-only cumulative snapshot for explicitly named dimensions, with measurement evidence/basis, finality and unknown reason, targeting the same attempt and unique reservation as its predecessor. Omitted dimensions remain unchanged, not zero or settled. A single writer validates and appends sequence `n+1` against the current head `n` in one transaction; receipt time does not determine ordering. Identical repeated observation keys/payloads are idempotent no-ops; reused keys with different payloads, stale predecessors, cross-attempt/reservation references, decreasing cumulative totals, or incompatible final totals are rejected and recorded as conflicts. An out-of-order receipt must be re-expressed against the current head with supporting evidence; a rejected observation changes no accounting. Corrections to final totals require a separate human-reviewed adjustment targeting that same head/attempt/reservation, preserving the old record and explaining authoritative correction evidence; they cannot silently overwrite history or release uncertain exposure.

Reservation `held|uncertain|settled|released` is only a summary projection: settled requires every applicable dimension final, and released requires proven zero consumption/not-sent. Recovery upper-bound charges remain labelled conservative, not measured; replacement by later actuals is atomic and removes only the matching conservative coverage. Never sum all observations or count both a recovery interval and the attempts it already covers.

## Privacy and tool permissions

All retrieved pages, documents, source excerpts and tool responses are untrusted evidence. Embedded requests to change instructions, disclose secrets, call tools or approve gates have no authority. The coordinator supplies structured data to roles; a deterministic tool broker checks actor, role, run purpose/mode, scoped authorisation, allowed action/arguments/destination, data classification, expiry, integration readiness and reservation on every invocation. Default deny applies outside an explicit allowlist. Denials are redacted audit events. Agents have no direct network, shell, credential or decision-store bypass. Human input enters through an explicit local approval interface with actor confirmation; this is a local single-user trust boundary, not a claim of independent identity assurance.

| Role | Potential tools after separate authorisation | Always outside that role's default permission |
| --- | --- | --- |
| Coordinator | Validate, schedule, persist sanitised artifacts/checkpoints, evaluate gates; dispatch through broker | Invent human decisions, change own policy, arbitrary shell/network |
| Discovery, market, competition, regulatory | Approved public search/read and evidence extraction; demo fixtures locally | Customer contact, authenticated/private browsing without specific grant, coding, financial operations |
| Economics | Read approved evidence; deterministic sandboxed calculations | Arbitrary executable content from sources, financial transactions |
| Independent reviewer | Read/challenge evidence and calculations; separately allowed public retrieval | Human acceptance, expanded permissions, source-driven actions |
| Validation | Read approved sanitised customer references; protocol/findings artifacts | Outreach, private record access or exports without explicit data/contact grants |
| Product, architecture | Read accepted artifacts, write proposals | Code execution, deployment, acquisition of infrastructure |
| Engineering | Scoped workspace edits and approved test commands only for authorised implementation tasks | Commit/push, install, external calls or deploy without specific authority |
| Code review, QA | Read scoped changes; authorised isolated tests with synthetic data | Release approval, unrestricted shell/network, production mutation |
| Human review owners | Review and record decisions within assignment | Implicit spending, outreach or release execution from artifact acceptance alone |

Public retrieval must constrain redirect destinations, local/private network addresses, schemes, download sizes and timeouts; never expose credentials to retrieved destinations. Secret resolution happens only inside an approved adapter from an external store, with redaction before persistence. Prompts/outputs may leak private data: allowlisted field filtering and data-access checks precede provider transmission; private customer payloads are denied by default. Keep credentials, identity maps and raw interview records outside repository artifacts and Git. Ignore patterns are not access controls. Retention/access/export policy for future real customer records must be approved before collection. No external tool execution, outreach, coding or deployment is authorised by this document or performed in FRA-003.
